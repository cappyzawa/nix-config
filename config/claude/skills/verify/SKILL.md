# Verify

変更が「動く」ことを実行で確かめる skill。コードが変わったことと機能が動くことは別で、後者を証明するのがここの責務。判定を出すところまでで、FAIL は直さずに報告する（修正するかは呼び出し元が裁定する）。

固定チェックリストではない。**diff から検証対象を導く。** 入力のない設定変更に「境界値」を試しても無意味で、逆に並行処理に「正常系 1 本」では足りない。

## 手順

### 1. 変更 surface を分類する

```
git diff --name-only HEAD
git diff HEAD
```

diff の中身を読み、下表のどの surface に当たるかを列挙する。1 つの変更が複数に当たることは普通にある。

### 2. surface ごとに検証項目を起こす

| 変更 surface | 検証すべき観点 |
|---|---|
| 純関数・変換・表示ロジック | 入力範囲の端を系統的に（空・境界・最大・不正）。「正常系 + 異常系 1 つ」で止めない |
| 呼び出し位置の移動・責務の移動 | 呼び出し元を**全部**数える（grep を狭い範囲で打ち切らない）。移動によって失敗の順序が変わらないか |
| 設定ファイル・定義ファイル | そのキーが実際に読まれるか、**読み取り側のコードで**確認する。セクション名まで合っているか |
| I/O・読み取り位置の変更 | 読み取りと使用の間に**他者が何を変えるか**。窓が広がっていないか |
| 並行処理・ロック | ロックの取得順序、deadlock cycle の新設、race の窓。既存の経路と逆順になっていないか |
| 終了経路・shutdown・cleanup | 終了経路を**全部数える**。exit code を assert する。待機を解除した後に残るハンドルと、exit 以外のイベント（error / EPIPE） |
| migration・デプロイ順序 | 適用順序。部分失敗と再試行。旧コード×新スキーマと新コード×旧スキーマの両方 |
| 観測系・メトリクス | **実データを 1 本引く**。label や形状を推測で書かない |
| 生成物・golden・snapshot | 再生成してから assert する。CI と同じ手順で回す |
| UI・表示 | データ窓と表示窓の区別。丸め方式とバケット境界の整合。タイムゾーン境界 |
| IAM・権限・deny | action の列挙漏れ。rollback 経路が残っているか |
| e2e の完了待ち | 「消える / 変わる UI」を完了シグナルにするなら、それが**何をトリガに変わるか**をコードで確認する |

表に無い surface は自分で観点を起こす。表は網羅ではなく出発点。

### 3. 実行して証拠を残す

項目ごとに次の形式で出力する。これが完了判定の唯一の材料になる。

```
- 項目: <何を確かめるか>
  コマンド: <実行したもの>
  期待: <どうなれば PASS か>
  実際: <出力の該当部分>
  判定: PASS / FAIL (regression) / FAIL (既存) / 実行不能
```

判定が語るのは**検証対象の挙動が期待と一致したか**だけ。コマンドが exit 0 でも期待と違えば FAIL で、検証自体を回せなかった場合だけ「実行不能」。

FAIL は変更前の版で同じ検証を回して切り分ける。変更前は期待どおりだった → `regression`、変更前も同じだった → `既存`。変更で新設した性質が一部の入力域で未達というだけなら `既存` に落ちるので、期待欄にその性質を書いて読み手が取り違えないようにする。

変更前の版は `git archive HEAD | tar -x -C <dir>` で実行可能な木ごと、検証対象の作業ツリーの外（scratchpad など）へ取り出す（単一ファイルの `git show` では import が解決せず、`git stash` や `git checkout` は検証対象そのものを消す）。**切り分けのために検証する経路を変えないこと。** 変更した名前（引数名・設定キー）で呼ぶ経路はそれ自体が検証対象で、名前を避けた経路に移すと破損が視界から消える。変更前では回せない項目は、変更前の版に同等の入力条件（旧名の入力、新スキーマ × 旧コード）を作って比べる。

### 4. 回せなかったものを明示する

環境要因（OOM、依存の不足、権限）で飛ばした検証は「実行不能」として理由付きで残す。**黙って省略しない。**

## 譲れない 3 点

- **自己申告を根拠にしない。** subagent や前のターンの「PASS した」を証拠として扱わない。自分でコマンドを回して出力を見る
- **end-to-end で動くことを確認する。** ユニットテストが通ることは、機能が動くことの証明にならない。runtime surface があるなら実際に起動して通す
- **飛ばした検証を黙って省略しない。** 回していない検証を回したことにしない

## 安全境界

- 実データを引く検証は **fixture / staging / read-only を原則**とする
- **production への接続・書き込み、副作用のある e2e は自走しない。** 必要ならユーザーに確認する
- 秘密情報（token、接続文字列、個人データ）を出力に出さない。マスクするか、値ではなく形状を確認する

## 収束しないとき

同じ項目で 2 周しても PASS も FAIL も確定しない場合は、そこで止めてユーザーに投げる。何が確定していないかと、確定に必要なものを書く。
