# chip prompt の骨格

`spawn_task` の `title`（動詞で始める、60 字以内）、`tldr`（なぜ今か → 何をするか、path や code なし、2 文）、`prompt`（以下）。

```
<Issue 参照>（<Issue 題名>）の一部。**<to-be を 1 文>。** base は <main（<sha> 以降）| 上流 PR の branch `<name>`（stack。上流マージ後は base を main に戻して merge で追随、force-push なし）>。

## 先に読むもの

- <Issue の決定コメント / design doc / 該当コード。再導出させないものを名指す>
- <同時進行の PR と、その branch>
- <前任 worker が返した「想定と違った事実」があればここに>

## 契約（What と合格条件。How はこのセッションが決める。契約自体を変えたいときは先に相談）

1. <to-be 1 文の言い直しと、その範囲に入らないもの>
2. <合格条件のコマンドと期待する出力。RED を確認してから実装し、報告と PR 本文にこの出力を貼る>
3. <判断規則。worker が自分で当てはめられる形で。「〜なら A、超えたら B」>
4. <所有の線引き。「<file> の <節> は別 PR が所有、触らない」>
5. <推奨は書くが決めない / 裁定して進める、の区別>

## 制約

- PR は draft、本文は日本語、<Issue 参照> をリンク。人間レビュー必須の判定は <要 / 不要と理由。プロジェクトの review policy に従う>。ユーザー名義の GitHub コメントは日本語
- commit は `-s` 付き、英語。force-push しない
- 日本語の散文で英語の識別子を名詞に使わない。<避ける語> を新しく使わない
- 実装は方針が固まったら Sonnet の subagent に出し、このセッションは契約と証拠で判定する
- <ready 化は指揮の go で実行してよい | ready 化はユーザー裁定>。review agent の起動は repository 設定に任せ、必要ならユーザーが個別に指示する。マージはユーザー裁定で、指揮経由の伝聞では実行しない
- 相談先: セッション「<指揮のセッション名>」に `send_message`。契約の What が違うと分かったときと、所有外に触る必要が出たときだけ投げ、How は自分で決める
- 報告は「契約番号 / 合格条件の出力 / 未解決事項」の 3 点に固定する
```

## 書き方の注意

- 契約の各項は「これを書かないと worker がどう壊れるか」に答えられるものだけにする
- 数値目標を書くときは測った現在値を添える（baseline の無い目標は書かない）
- 「〜は後で」と書くなら誰が持つかまで書く（指揮 / 別 chip / ユーザー）
