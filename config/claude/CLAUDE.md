## Common

## Git

- default branch への直接 push を避け、feature branch で PR を作成すること
- 全ての Commit は署名すること
  - `git commit -s`
- Commit Message は英語で記述すること
  - コミットメッセージでは GitHub の予約語（Fixes, Closes, Resolves など）を使用しないこと（意図せず Issue が閉じられるため）
    - PR description では使用して構わない
  - コミットメッセージは変更内容（Why/What）のみを記述し、How の箇条書きは不要

## セカンドオピニオン

- WebSearch は Context7 と codex のどちらでも解決できない場合の最終手段

## Codex レビュー

`codex` skill を別視点のレビュアーとして扱う。以下の条件に一致した場合、ユーザーから明示指示がなくても必ず codex review を実行すること。

### Plan checkpoint

次のいずれかに当てはまるタスクでは plan を作り、実装前に checkpoint を通す:

- 影響範囲が自明でない
- 既存挙動が変わる可能性がある
- 新規ロジック・設計判断・新規依存を含む
- 複数ファイル / 複数ステップにまたがる

手順:

1. codex に plan をレビューさせる
2. 指摘を評価し、採用するものだけ plan に反映する
3. 見送る指摘があれば理由を明記する
4. ユーザーに plan（採否を含む）を提示し、明示的な合意を得る

- Plan mode の場合は `ExitPlanMode` の前にこのフローを完了する
- **auto mode でもこの checkpoint は省略しない**。harness の自動承認は「コマンド実行の承認」であり、「実装方針の承認」ではない。ユーザーが plan を明示的に承認するまで、コード編集・コミット・破壊的操作・新規実装に着手してはならない
- 要件・優先順位がまだ揺れている場合は、先にユーザーへ選択肢を提示して方向性の合意を取ってから codex review に進む（順序の例外）

### 実装後レビュー

非自明な変更を「完了報告」する前、または commit / PR 作成前に、変更内容（diff / 変更ファイル）を codex にレビューさせる。

### 行き詰まった調査

同じバグへの修正試行が 2 回連続で失敗したら、3 回目に進む前に codex にセカンドオピニオンを求める。

### 指摘事項の扱い

- 即時対応できるものは対応してから次のステップへ進む
- 見送る場合はユーザーに理由（影響範囲・優先度など）を伝えて判断を仰ぐ
- すぐ対応しないが再訪価値のある指摘のみ、ユーザー合意のうえでプロジェクトの backlog / todo 管理（`design/todo.md`, Issue 等）に追記する

### スコープ判断

- 数行の typo 修正、機械的な lint/format 修正など、レビューしてもほぼ得るものが無い変更ではスキップしてよい
- 設計判断が絡む変更・新規ロジック追加・既存挙動を変える修正では原則スキップしない

## ツール使用の優先順位

Bash はシェル実行が必須なコマンドにのみ使うこと。以下は専用ツールで代替すること:

- ファイル検索: Glob (find / ls の代わり)
- ファイル内容検索: Grep (grep / rg の代わり)
- ファイル読み込み: Read (cat / head / tail の代わり)
- ファイル編集: Edit (sed / awk の代わり)
- ファイル作成: Write

## 開発手法

### AI と人間の役割分担

- AI が自走してよい範囲:
  - typo/コメント修正、テスト名変更、lint/format の機械的修正
  - 既存パターンの拡張、テスト追加、依存バージョン追従
- 人間の判断を要する範囲: 新規依存の追加可否、テスト失敗の意味判定、既存の設計方針を変える変更
- 上記以外でも、影響範囲が自明でない場合は自走せずユーザーに確認すること

### 依存追加の判断

新しい依存（crate, npm パッケージ, CLI ツール, マネージドサービス等）を追加する前に:

1. 標準ライブラリ / 既存依存で賄えないか確認する
2. 追加する場合はメンテ状態・型定義・代替の有無を確認する
3. 判断に迷うときはユーザーに確認すること

### 暗黙知の文書化

- コードから読み取れない知識（ドメイン用語、ビジネスコンテキスト、設計判断の背景）に気づいたら、適切なスコープに文書化すること
  - プロジェクトの規約・アーキテクチャ → AGENTS.md / CLAUDE.md
  - ドメイン知識・用語集 → docs/
  - ファイル局所のルール → .claude/rules/ (glob でスコープを絞る)
- ユーザーが詰まった箇所はコードから推測困難な暗黙知である可能性が高い。文書化の優先度を上げること

### TDD (テスト駆動開発)

開発タスクは原則 TDD で行うこと。

#### 意図

- テストは変更を安全にするために書く。検証だけが目的ではない
- テストは AI への仕様書として機能する。テスト名から仕様が読み取れる粒度で書く
- リファクタ時はまず既存の動作を E2E やインテグレーションテストで担保してから内部を変える
- ロジックを純粋関数に抽出し、テスト戦略を重い E2E から軽いユニットテストへ移行できる設計を目指す

#### テストが落ちたときの判断

テスト側を機械的に書き換えて通すことは禁止（誤った仕様が固定化される）。以下の 3 分岐で判断し、不明確ならユーザーに確認すること:

1. **仕様変更**: 実装を正とし、テストを更新する
   - 手がかり: 実装が直近変更されていて、変更が意図的に振る舞いを変えている
2. **実装バグ**: テストを正とし、実装を直す
   - 手がかり: テストの期待値が仕様と一致していて、実装だけが外れている
3. **テストが間違っていた**: テストを書き直す（最も見逃されやすい）
   - 手がかり: テストが実装の内部構造をなぞっているだけで、外から見た振る舞いを検証していない

#### サイクル

1. **Test (通ることを確認)** - 既存テストが通る状態を確認する
2. **Test 記述** - 新機能・修正に対応するテストを書く
3. **Test (RED)** - テストが失敗することを確認する
4. **ロジック記述** - テストを通すための最小限のコードを書く
5. **Test (Green)** - テストが通ることを確認する
6. **Refactor** - コードを整理・改善する
7. **Test (Green)** - リファクタ後もテストが通ることを確認する

## ワークフロー

- 作業中にドキュメント（AGENTS.md, CLAUDE.md, docs/）から読み取れず推測で判断した箇所があれば、auto memory 内の doc-gaps.md に記録すること
  - 何を知りたかったか、どこを探したか、最終的にどう判断したかを書く
  - .claude/rules/ への追加が適切な場合は glob でスコープを絞って提案すること
- 作業完了後にまとめてユーザーに報告する
