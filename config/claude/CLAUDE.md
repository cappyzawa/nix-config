# CLAUDE.md

## Common

- 会話は基本的に日本語で行うこと
  - 全角と半角の間には半角スペースを入れること
  - 会話が日本語であれば構わないため、Thinking は英語でも問題ない
- 絵文字は使わない。機構が必須とするもの（Artifact の favicon など）は対象外
- 箇条書きは 1 アイテム 1 文とし、収まらないなら項目を分割するか散文で書く
- コードコメントは英語で記述すること
- コメントはコードから読み取れないことだけに絞る
  - 命名・型・構造で説明できるものは、コメントを足さずそちらを直す
  - 書いてよい典型: この形を選んだ理由、外部由来の制約（依存の bug・API の仕様・互換）、コードに現れない不変条件や前提
  - 書かない典型: 処理の逐語訳、識別子名の言い換え、セクション見出し、作業の実況（「〜を追加した」）
  - 迷ったら書かない

## Git

- default branch への直接 push を避け、feature branch で PR を作成すること
- 全ての Commit は署名すること
  - `git commit -s`
- Commit Message は英語で記述すること
  - コミットメッセージには GitHub の予約語（Fixes, Closes, Resolves など）と Issue/PR への参照（`#N`, `org/repo#N`, URL）を書かないこと
    - 予約語は意図せず Issue を閉じ、`#N` 参照は commit が push されるたび Issue/PR 側タイムラインに無駄な backlink を生む
    - Issue/PR への参照は PR body に置く（§PR description 参照）
  - コミットメッセージは変更内容（Why/What）のみを記述し、How の箇条書きは不要
- ready 後の修正は force-push で履歴を書き換えず commit を足す（レビュアーが自分のレビュー以降の差分を追えるようにする）

## Issue

- Issue は課題にフォーカスする。「何が問題か・なぜ問題か・どうなっていれば解決か」を書き、実装方法まで踏み込まないこと。解決策を書き込みすぎると要件に見え、着手時の設計の幅を狭める
- 書くこと: 現状と問題（観測した事実・再現手順・エラー出力）、なぜ問題か（影響範囲・優先度の判断材料）、期待する状態（How ではなく What で）
- 調査で得た手がかり（該当コードの場所・原因の仮説）は着手者に有用なので書いてよい。ただし事実と仮説を明確に区別し、調査メモとして要件と混ぜないこと
- 書かないこと: 解決アプローチの提案、実装手順の指定、変更ファイルのリスト、コードレベルの詳細設計（いずれも着手時に決める。「案」として書いても着手者を anchoring して幅を狭める）
- Issue/PR への参照は `org/repo#N` 形式で書く（§PR description と同じ）
- リポジトリに Issue テンプレートがある場合はテンプレートに従い、このルールは各欄をどう埋めるかの指針として適用する

## Pull Request

- PR は初回作成時に必ず draft で作成すること
- レビュー準備ができたら別途 `gh pr ready` で解除する
- 破壊的変更（major バージョン更新、API 削除、依存の大規模入れ替え等）は単独 PR で出し、機能変更と混ぜないこと
- PR の merge 待ちの間に、その PR に依存する後続作業へ勝手に着手（stack）しないこと。stacked PR はユーザーが明示的に指示した場合のみ。PR と独立な別タスクへ進むのは構わない

### PR description

- 読み手は human レビュアー。merge 判断に必要な情報だけを書き、記録媒体として使わないこと
- 分量は diff の行数ではなくレビュアーの判断負荷に比例させる。機械的な大量変更は短く、レビュアーが判断に迷う数行こそ厚く書く
- 厚く書く前に「この diff でレビュアーが迷う点」を 1 つ具体的に挙げる。挙がらなければ各節 1〜3 文に収める。**調査が難しかったことは厚く書く理由にならない**（原因が判明した後の変更が自明なら短く書く）
- 書くこと: 動機（1〜2 文）、アプローチ（箇条書き 3〜5 点、per-file ではなく）、non-goals / follow-up
- 「特に見てほしい箇所」は、レビュアーの目を一点に引きたい具体的な理由があるときだけ足す
- 検証は独立した節を作らず、CI が示さない確認のうちレビュアーが実際に出す疑問に答えるものだけを該当アプローチの bullet に畳む
- **「追加でこれも回して緑だった」は書かない**（回した本数は論拠にならないし、CI Green 以上の情報にならない）
- コマンドや出力の貼り付けはレビュアーが再現する必要があるときだけ
- 関連 Issue/PR へのリンクと GitHub の予約語（Closes 等）は PR body ではむしろ推奨。参照は `org/repo#N` のように org/repo まで明示し、番号だけの `#N` による取り違えを防ぐ
- 書かないこと: ファイル別の変更列挙（diff の言い直し）、作業過程の物語（「まず調査し…」）、テンプレートに無い装飾や N/A 埋めの boilerplate
- 情報は寿命で置き場所を振り分ける。PR body に書いてよいのは merge 後に価値が消える情報のみ:
  - 症状・原因分析・再現手順 → Issue（PR からリンクするだけにして本文に再掲しない）
  - コードの特定箇所に紐づく非自明な Why → コードコメント（PR body で繰り返さない）
  - 変更自体の Why（なぜ今・なぜこの方針・捨てた代替案） → commit message
  - レビュー時にだけ意味がある情報（CI で示せない検証の結論・注視点・リスク） → PR body
- 原因分析・再現手順が Issue 側に無い（あるいは誤っている）場合は、PR body で埋め合わせる前にユーザーに相談する（PR を作る流れで Issue に書き込みが入るのは予想しにくい副作用になる）
- リポジトリに PR テンプレートがある場合はテンプレートに従い、このルールは各欄をどう埋めるかの指針として適用する

## セカンドオピニオン

- ライブラリの API ドキュメント・使い方を調べるときは Context7 MCP (`resolve-library-id` → `get-library-docs`) を優先する
- 設計判断・ベストプラクティス・技術的な正しさの検証には `codex` skill を使う
  - 詳細な使い方は `codex` skill 参照
- WebSearch は Context7 と codex のどちらでも解決できない場合の最終手段

## 証明の形を決める

着手前に main が決める。subagent に委譲しない。**「できた」の判定基準はループの停止条件そのもの**で、これを渡すと停止時点の判断が worker 側に漏れる。

- **現状を測る。** check を 1 回回して現在値を得る。現在値が出せないものは、まだ終了条件を書ける状態ではない
- **証明を実行可能な形にする。** コマンド、または自分で書く test / probe。散文の合格基準は停止条件にならない
- **設計を左右する仮定は着手前に証拠にする。** 該当コードを読むか 1 回動かす。「〜のはず」で進めない
- 委譲プロンプトにはその check を渡す。言語別 agent が回すのは固定の回帰チェック（`make check` / `cargo test` 等）で、それは「他を壊していない」ことしか言わない

## 検証

品質はレビューではなく実行で作る。**コードを変えたら動かして確かめる**のが既定で、レビュー層より優先度が高い。

- 手順は `verify` skill が持つ。diff から変更 surface を分類し、surface ごとの観点で検証項目を起こして実行する
- 証拠は transcript に残す（コマンド / 期待 / 実際 / 判定）。ターン終了時に Stop hook が「変更があるのにそれを動かした出力が無い」状態を検出して作業を継続させるので、証拠が出ていないと終われない
- Stop hook はスコープの取り落ちも見る。要求の一部を落とすなら理由を述べる（黙って縮めない）
- 同じ項目で 2 周しても確定しないときは止めてユーザーに投げる。連続ブロックは harness 側が 8 回で打ち切る

## Codex レビュー

`codex` skill を別視点のレビュアーとして扱う。以下の条件に一致した場合、ユーザーから明示指示がなくても必ず codex review を実行すること。

**このセクションのトリガーは main セッション（control plane）専用**。subagent として動作している場合は、条件に一致しても codex / devils-advocate を自分で起動しないこと。レビューが必要・判断に迷うと感じたら、その旨を結果報告に含めて main セッションに差し戻す。レビューの起動と指摘の裁定は main セッションの責務。

**codex 不在 host での fallback**: トリガーに入る前に `command -v codex` で存在確認すること。`codex` コマンドが無い host では、以下の手順内に出てくる `codex` をすべて `devils-advocate` subagent（Agent tool で起動）に読み替える。fallback は同モデル由来の盲点があるが、独立コンテキストで反対側の視点を出させる。codex も devils-advocate も使えない場合はレビューを黙ってスキップせず、その旨を報告してユーザーの判断を仰ぐ。

### 実装後レビュー

非自明な変更では、実装（subagent からの統合を含む）が揃った後、commit / PR 作成・完了報告の前に `land` skill を実行する。手順（verify → code-review --fix → codex レビュー → retro 記録）と各ステップの詳細は skill 側が持つ。どこまで走らせるかは「スコープ判断」に従う。

順序の意図: まず verify で動くことを確かめ、次に機械的に直せる指摘を code-review --fix で消化し、別モデルという貴重な視点 (codex) を仕様・設計の誤りに集中させる。verify を後ろに置くと、レビュー指摘の対応で入れた変更が未検証のまま残る。

### 行き詰まった調査

同じバグへの修正試行が 2 回連続で失敗したら、3 回目に進む前に codex にセカンドオピニオンを求める。

### 指摘事項の扱い

- モジュール分割・責務配置・依存方向・抽象の選択が誤っているという構造指摘は、修正に着手する前に「局所修正」と「スライス単位の再実装」を比較して裁定する。既存実装への投下コスト（動いている・テストが green）は判断材料にしない。実装が委譲時の契約に違反しているだけなら契約は変えず元の契約で再実装する。契約自体の誤りが判明した場合は実装を止めてユーザーに戻し、方針の合意を取り直してから再委譲する
- 即時対応できるものは対応してから次のステップへ進む。**先送りは既定にせず理由を要する**: 他リポジトリで自分が push できない、二択で結論が変わるためユーザーの判断が必要、のいずれにも当たらないなら、同じコードパス・同じ契約に属するものはこのセッションで仕上げる（記録して完了扱いにしない）。**PR の規模を理由にしない**。分割の判定は「やりたいことが 1 つにまとまっているか」であって行数ではない。同じ意図に属するなら一緒に直した方が読みやすく、意図が複数混ざる場合の扱いは §Pull Request の「破壊的変更は単独 PR」が持つ
- 見送る場合はユーザーに理由（影響範囲・優先度など）を伝えて判断を仰ぐ
- すぐ対応しないが再訪価値のある指摘のみ、ユーザー合意のうえでプロジェクトの backlog / todo 管理（`design/todo.md`, Issue 等）に追記する
- codex / PR レビューで同種の指摘が**別タスク・別 PR で** 2 回以上再発し、汎用ルールで予防できる場合は、個別対応に加えて規約側へ昇格し再発を仕組みで防ぐ。言語横断の慣習は `~/.claude/rules/<lang>.md`、プロジェクト固有の事情はそのプロジェクトの CLAUDE.md / rules に書く。単発の文脈依存な指摘は昇格せず backlog / todo 止まりにする（規約の過剰増殖を防ぐ。昇格先と追加の可否は §暗黙知と規約の置き場所 に従う）
- PR レビュー（AI / 人間）で critical な取り逃し（land を通したのに残っていたバグ・契約違反）が発覚したら、`~/.claude/retro/flow.md` に land skill の retro 記録と同じ書式で 1 行追記する。集計と層調整の提案は `/chore flow-retro` が行う

### スコープ判断

レビュー層は変更規模でゲートし、全部盛りを既定にしない（レビューは valid でも diminishing returns がある）:

- 数行の typo 修正、機械的な lint/format 修正など、レビューしてもほぼ得るものが無い変更では全てスキップしてよい
- 小規模だが機械的でない変更（数ファイル以内・設計判断なし）は code-review --fix のみで codex を省略してよい
- ただし小規模でも、公開 API / 認証認可 / 永続データ・migration / infra の destroy・replace / 並行処理 / セキュリティ境界 / テスト期待値の変更を含む場合は codex を省略しない
- 設計判断が絡む変更・新規ロジック追加・既存挙動を変える修正では原則スキップしない（実装後レビューのフルパス: verify → code-review --fix → codex）
- **verify はこのゲートの対象外**。数行の typo やコメント修正を除き、コードを変えたら必ず動かして確かめる

## サブエージェントへの委譲

Agent tool の起動に、起動ごとのユーザー確認は要らない。自動起動させたくない skill は frontmatter の `disable-model-invocation: true` で個別に止める。

メイン会話は control plane として計画・レビュー・統合に徹し、作業本体は subagent に委譲する。tool 出力（ファイルダンプ・検索結果）をメイン context に溜めず、結論だけ受け取ることが目的:

- 複数ファイル・複数箇所にまたがる調査は Explore subagent に委譲する
- まとまった実装は言語別 agent (nix / rust / typescript / terraform) に委譲する
- 自分でやってよいのは、対象が特定済みの pinpoint な読み書きと、委譲のオーバーヘッドが作業本体を上回る小さな修正
- 委譲プロンプトにはタスクの契約・対象ファイル・合格基準（§証明の形を決める で作った実行可能な check）を明示的に書く。subagent はここまでの会話を見ていない
- 独立なタスクは単一メッセージで複数の実装 agent を並列起動する。同一ファイルに触れる恐れがあるスライス同士だけ `isolation: worktree` で分離する（Agent tool のパラメータ。人間向けの並行セッションを起動する worktree skill とは別物）
- 実装 agent の model は既定 sonnet（契約が固まっていれば十分で、レビュー側に強いモデルを残す構図）。契約外の判断が多く残りそうな難しいスライスだけ、Agent tool 呼び出し時の `model` 指定で上位モデルに上げる（呼び出し時指定が agent 定義の frontmatter より優先される）
- 委譲を起動するときの Agent tool の `name` は `<役割>-<model>-<effort>` の固定形式にする（例: `nix-slice1-sonnet-inh`, `verify-contract-opus-high`）。model は解決した実効値（呼び出し時指定 > agent 定義の frontmatter > session 継承）を常に書く。effort は明示指定した値、未指定なら `inh`（session 継承）と書く。全項目必須なので、形式を欠く名前は「書き忘れ」と判別できる。既定の層から変えた場合は理由を visible text で 1 行添える
- 委譲プロンプトの末尾に「完了したら `SendMessage({to: "main"})` で結論本文を送ること」を明記する（`name` を付けた agent はバックグラウンド起動になり plain text の最終出力が親に届かないため、これが無いと結論を返さず idle で止まる）

## 開発手法

### AI と人間の役割分担

- AI が自走してよい範囲:
  - typo/コメント修正、テスト名変更、lint/format の機械的修正
  - 既存パターンの拡張、テスト追加、依存バージョン追従
- 人間の判断を要する範囲: 新規依存の追加可否、テスト失敗の意味判定、既存の設計方針を変える変更
- 上記以外でも、影響範囲が自明でない場合は自走せずユーザーに確認すること

### 依存追加の判断

新しい依存（crate, npm パッケージ, CLI ツール, マネージドサービス等）を追加する前に:

1. 標準ライブラリ / 既存依存で賄えないか確認する
2. 追加する場合はメンテ状態・型定義・代替の有無を確認する
3. 判断に迷うときはユーザーに確認すること

### 暗黙知と規約の置き場所

コードから読み取れない知識に気づいたとき、規約を足したくなったときは、**強制力が高く対象に近い置き場所を優先し、下位で保持できるものを上位に上げない**:

コードで自明にする（アーキテクチャはディレクトリ構造・モジュール境界・型で、ドメイン用語は命名で表現する。守らせたい制約は誤りを選べない形にする）→ lint / テストで機械的に落とす → 局所のコードコメント → `docs/`（コードに現れない業務知識・用語集）→ `.claude/rules/`（glob でスコープを絞る）→ プロジェクトの CLAUDE.md / AGENTS.md → グローバル CLAUDE.md

- 上位ほど毎セッション読み込まれ、対象から離れるので陳腐化に気づけない。**アーキテクチャを散文で書く前に、ディレクトリ構造と型がそれを語れていないかを確認する**
- 変更自体の Why は commit message に置く（§PR description の寿命による振り分けに従う）
- ユーザーが詰まった箇所は推測困難な暗黙知である可能性が高い。ただし優先するのは文書化ではなくコード側での解消
- 規約（CLAUDE.md、`.claude/rules/`、skill、agent 定義）とコードコメントに 1 行足すときは、どの層でも「**これを書かないとどう壊れるか**」に答えられることを条件にする。答えられない典型は、harness が既に供給している記述（tool の description が指示済み）と、指示が無ければモデルがそもそもやらない類
  - **コード自体はこの基準の対象外。** 自己説明的にするための命名・型・構造は、厳密には「書かなくても壊れない」ものを含んでよい
- 編集では削除・反転・移動を先に検討し、追加は最後に置く。「削除した規約の後始末として足したガード」は、元の規約を消せば発生しない失敗を防ぐだけの死んだ記述になる
- **規約を削除するときは、その記述が運んでいた義務を列挙し、引き受け先を決める。引き受け先が無いものは削除しない。** 失われた義務は不在なので diff に現れず、レビューでも検出されない

### TDD (テスト駆動開発)

開発タスクは原則 TDD で行うこと。

#### 意図

- テストは変更を安全にするために書く。検証だけが目的ではない
- テストは AI への仕様書として機能する。テスト名から仕様が読み取れる粒度で書く
- リファクタ時はまず既存の動作を E2E やインテグレーションテストで担保してから内部を変える
- ロジックを純粋関数に抽出し、テスト戦略を重い E2E から軽いユニットテストへ移行できる設計を目指す

#### テストが落ちたときの判断

テスト側を機械的に書き換えて通すことは禁止（誤った仕様が固定化される）。以下の 3 分岐で判断し、不明確ならユーザーに確認すること:

1. **仕様変更**: 実装を正とし、テストを更新する
   - 手がかり: 実装が直近変更されていて、変更が意図的に振る舞いを変えている
2. **実装バグ**: テストを正とし、実装を直す
   - 手がかり: テストの期待値が仕様と一致していて、実装だけが外れている
3. **テストが間違っていた**: テストを書き直す（最も見逃されやすい）
   - 手がかり: テストが実装の内部構造をなぞっているだけで、外から見た振る舞いを検証していない

#### サイクル

1. **Test (通ることを確認)** - 既存テストが通る状態を確認する
2. **Test 記述** - 新機能・修正に対応するテストを書く
3. **Test (RED)** - テストが失敗することを確認する
4. **ロジック記述** - テストを通すための最小限のコードを書く
5. **Test (Green)** - テストが通ることを確認する
6. **Refactor** - コードを整理・改善する
7. **Test (Green)** - リファクタ後もテストが通ることを確認する
