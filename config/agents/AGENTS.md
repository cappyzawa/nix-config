# AGENTS.md

## Common

- 会話は日本語で行う（Thinking は英語でもよい）
- 日本語を書くときは `japanese-tech-writing` skill を読み、その規範に従う
- 絵文字は使わない（Artifact の favicon のように機構が必須とするものは対象外）
- PR、Issue、docs の言語は repository の公開範囲で決め、public は英語、internal と private は日本語にする
- Codex では、変更対象の言語に対応する `~/.agents/rules/<language>.md` があれば作業前に読む
  - Claude Code は同じ本文を path-scoped rule として自動で受け取る
- 書ける分量の上限は、結論を支える証拠の量である
  - 会話、PR や Issue の本文、commit message、docs のすべてで、結論を支える証拠だけを書く
  - 断定は、読んだコード、実行した出力、ユーザーの明示発言で直接確認した範囲にだけ使う
  - 直接確認していない原因、影響、意図は仮説として、合意していない方針は提案として書く
  - 渡された「確認済み」は、添えられた証拠が支える範囲でしか引き継がない
  - 証拠の無い部分を文章量で埋めない
- コードの位置は既定では書かず、必要なときだけ commit を固定した GitHub の permalink にする
  - 引用したツール出力の中の行番号は残す
- コードコメントは英語で書く
- コメントはコードから読み取れないこと（この形を選んだ理由、外部由来の制約、コードに現れない不変条件）だけに絞る
  - 命名、型、構造で説明できるものは、コメントを足さずそちらを直す
  - 迷ったら書かない

## Git

- default branch へ直接 push せず、feature branch から PR を作る
- すべての commit に `git commit -s` で署名する
- commit message は英語で書き、変更の Why と What だけを載せる
- commit message に GitHub の予約語（Fixes、Closes、Resolves など）と Issue や PR への参照（`#N`、`org/repo#N`、URL）を書かない
  - 予約語は意図せず Issue を閉じ、`#N` 参照は push のたびに Issue や PR のタイムラインへ backlink を生む
  - Issue や PR への参照は PR body に置く

## Issue と Pull Request

- Issue の本文は `issue` skill、PR の作成と本文は `pull-request` skill の規範に従う
- PR は必ず draft で作り、レビュー準備ができたら `gh pr ready` で解除する
- ready 後の修正は force-push せず commit を足す
- Issue や PR への参照は `org/repo#N` 形式で書く

## 役割分担

- Why と What はユーザーと main セッションで決める
  - to-be を 1 文で言えるまで詰める
  - Issue や prompt に書かれていなければ、推測で埋めずにユーザーに聞く
- How は main セッションが持つ
  - 手順、分解、検証の設計は main の責務で、ユーザーに承認を求めない
  - 設計を左右する仮定だけは、着手前に該当コードを読むか 1 回動かして証拠にする
- 「〜を調べたい」「〜について考えたい」は調査依頼として扱い、成果物を作らず結論と根拠で終える
- 完了は自己申告ではなく実行結果で判定する
  - コードを変えたら動かして確かめ、コマンド、期待、実際を transcript に残す
  - 手順が要るときは `verify` skill を使う
- 同じバグへの修正が 2 回連続で失敗したら、3 回目に進む前に別モデルの視点（Claude Code では `codex` skill）を入れる

## レビュー

- commit 前の多段レビュー（観点別 fan-out、独立 reviewer、品質パスの skill）は行わない
  - 読んで見つかる誤りは、PR 上の Code Review agent と人間が担う
- commit 前に main が自分で diff を一度読み直す
- それ以上のレビュー層は、ユーザーが求めたときだけ足す
- `codex` は、別モデルと別 context の視点が要る設計判断やセカンドオピニオンに使い、定常工程にはしない
- ライブラリの API と使い方は Context7 MCP（`resolve-library-id` の後に `get-library-docs`）を優先する
- WebSearch は Context7 で解決できないときの最終手段にする
- 即時対応できる指摘はその場で直す
- 見送る指摘は、理由を添えてユーザーに判断を仰ぐ
- fail-open を勧める指摘はそのまま採らない
  - 採るなら「どの条件で通すか」を列挙し、その条件が既定経路にならないことを実際に発火させて確かめる

## サブエージェント

既定は single agent で、main が自分で読み、書き、動かす。
subagent を起こすのは次の 3 つが揃うときだけにする。

1. 互いに独立で並列に進められる作業がある（型、API の形、fixture のような短い契約を先に固定すれば独立になるものを含む）
2. subagent が main と異なる情報、model、tool、権限を持つ
3. agent を 1 つ足す利益が、token、待ち時間、誤り伝播のコストを上回る

同じ model と入力に役名だけを変えた「実装者と reviewer」は、2 を満たさないので理由にならない。

- agent を足す前に依存グラフを描く
  - 作業を書き込み先のファイル集合で分ける
  - ノード間の依存を「コードの依存」と「呼び出しや実行時の辺」に分ける
- 並列にするのは、コード依存が残らず、書き込み先も重ならないノードだけにする
  - 呼び出し辺だけが残るなら、被呼び出し側の型、シグネチャ、fixture を契約として先に凍結し、依存をその成果物へ移してから並列にする
- 次の編集が前の編集の実コードを必要とするなら、single のまま進める
- 2 つの作業が同じファイルに書くなら、single のまま進める
  - worktree は衝突を先送りするだけで消さない
- subagent に渡すのは契約（目的、対象ファイル、書き込み範囲、合格条件）と上流の成果物で、会話履歴は渡さない
- subagent に返させるのは patch、証拠、未解決事項で、transcript は返させない
- 統合と trunk への書き込みは main だけが行う
- 調査の fan-out は、1 件の lookup に 1 agent、比較に 2〜4、広い調査にだけ 10 以上を目安にする
- model と effort は agent 定義の既定に任せる
  - 起動時に変えたときは、理由を visible text に 1 行添える
- harness が agent 名を受け取る場合、名前は `<役割>` とし、model や effort を指定したときだけ `<役割>-<model>-<effort>` にする

## 開発手法

### AI と人間の役割分担

- AI が自走してよいのは、typo とコメントの修正、テスト名の変更、lint と format の機械的修正、既存パターンの拡張、テスト追加、依存バージョンの追従である
- 人間の判断を要するのは、新規依存の追加可否、テスト失敗の意味判定、既存の設計方針を変える変更である
- 上記以外でも、影響範囲が自明でない場合は自走せずユーザーに確認する

### 依存追加の判断

新しい依存（crate、npm パッケージ、CLI ツール、マネージドサービスなど）を追加する前に、次の順で確認する。

1. 標準ライブラリか既存依存で賄えないかを確認する
2. 追加するなら、メンテ状態、型定義、代替の有無を確認する
3. 判断に迷うときはユーザーに確認する

### 暗黙知と規約の置き場所

コードから読み取れない知識に気づいたとき、または規約を足したくなったときは、強制力が高く対象に近い置き場所を優先する。
下位で保持できるものを上位に上げない。
置き場所を強制力の高い順に並べると次になる。

1. コードで自明にする（アーキテクチャはディレクトリ構造、モジュール境界、型で、ドメイン用語は命名で表現し、守らせたい制約は誤りを選べない形にする）
2. lint やテストで機械的に落とす
3. 局所のコードコメント
4. `docs/`（コードに現れない業務知識、用語集）
5. path scoped rules や nested `AGENTS.md`
6. プロジェクト root の `AGENTS.md`
7. グローバル `AGENTS.md`

- 上位ほど毎セッション読み込まれ、対象から離れるので陳腐化に気づけない
- アーキテクチャを散文で書く前に、ディレクトリ構造と型がそれを語れていないかを確認する
- 変更自体の Why は commit message に置く（`pull-request` skill の情報の置き場所に従う）
- ユーザーが詰まった箇所は、推測困難な暗黙知である可能性が高い
  - それでも優先するのは文書化ではなく、コード側での解消である
- 規約（`AGENTS.md`、path scoped rules、skill、agent 定義）とコードコメントに 1 行足すときは、「これを書かないとどう壊れるか」に答えられることを条件にする
  - 答えられない典型は、harness が既に供給している記述（tool の description が指示済み）と、指示が無ければ model がそもそもやらない類である
  - コード自体はこの基準の対象外で、自己説明的にするための命名、型、構造は「書かなくても壊れない」ものを含んでよい
- 編集では削除、反転、移動を先に検討し、追加は最後に置く
  - 「削除した規約の後始末として足したガード」は、元の規約を消せば発生しない失敗を防ぐだけの死んだ記述になる
- 規約を削除するときは、その記述が運んでいた義務を列挙し、引き受け先を決める
  - 引き受け先が無いものは削除しない
  - 失われた義務は不在なので diff に現れず、レビューでも検出されない

### TDD (テスト駆動開発)

開発タスクは原則 TDD で行う。

#### 意図

- テストは変更を安全にするために書き、検証だけを目的にしない
- テストは AI への仕様書として機能するので、テスト名から仕様が読み取れる粒度で書く
- リファクタ時は、まず既存の動作を E2E やインテグレーションテストで担保してから内部を変える
- ロジックを純粋関数に抽出し、テスト戦略を重い E2E から軽いユニットテストへ移行できる設計を目指す

#### テストが落ちたときの判断

テスト側を機械的に書き換えて通すと誤った仕様が固定化されるので、行わない。
次の 3 分岐で判断し、不明確ならユーザーに確認する。

1. **仕様変更**：実装を正とし、テストを更新する
   - 手がかりは、実装が直近変更されていて、その変更が意図的に振る舞いを変えていることである
2. **実装バグ**：テストを正とし、実装を直す
   - 手がかりは、テストの期待値が仕様と一致していて、実装だけが外れていることである
3. **テストが間違っていた**：テストを書き直す（最も見逃されやすい）
   - 手がかりは、テストが実装の内部構造をなぞっているだけで、外から見た振る舞いを検証していないことである

#### サイクル

1. 既存テストが通る状態を確認する
2. 新機能や修正に対応するテストを書く
3. テストが失敗すること（RED）を確認する
4. テストを通すための最小限のコードを書く
5. テストが通ること（Green）を確認する
6. コードを整理し改善する
7. リファクタ後もテストが通ることを確認する
