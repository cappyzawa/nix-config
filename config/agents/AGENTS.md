# AGENTS.md

## Common

- 会話は日本語で行う
  - Thinking は英語でもよい
- 全角と半角の間には半角スペースを入れる
- 絵文字は使わない
  - Artifact の favicon のように機構が必須とするものは対象外にする
- Codex では、変更対象の言語に対応する `~/.agents/rules/<language>.md` があれば作業前に読む
  - Claude Code は同じ本文を `~/.claude/rules/` の path-scoped rule として自動で受け取る
- 箇条書きは 1 アイテム 1 文にする
  - 1 文に収まらないなら項目を分割するか、散文で書く
- 書ける分量の上限は、結論を支える証拠の量である
  - 会話、PR と Issue の本文、commit message、docs のすべてに適用する
  - 結論を支える証拠は、コマンドと出力やコードの引用を添えて詳しく書いてよい
  - 結論を支えない調査結果は、証拠があっても落とす
  - 断定は、読んだコード、実行した出力、ユーザーの明示発言で直接確認した範囲にだけ使う
  - 渡された「確認済み」は、添えられた証拠が支えている範囲でしか引き継がない
  - 直接確認していない原因、影響、意図は仮説として書く
  - ユーザーと合意していない方針は提案として書く
  - 証拠の無い部分を文章量で埋めない（造語と対句が出るのはここである）
- コードの位置は既定では書かない
  - 必要なときだけ、commit を固定した GitHub の permalink にする
  - `path:行番号` は更新で動き、壊れたことに読み手が気付けない
  - 引用したツール出力の中の行番号は残す
- PR、Issue、docs の言語は repository の公開範囲で決める
  - public では英語、internal と private では日本語にする
- 日本語で書くときは `japanese-tech-writing` skill を読み、その規範に従う
  - 対象は会話での説明、PR と Issue の本文、docs、レビュー返信である
- コードコメントは英語で書く
- コメントはコードから読み取れないことだけに絞る
  - 命名、型、構造で説明できるものは、コメントを足さずそちらを直す
  - 書いてよい典型は、この形を選んだ理由、外部由来の制約（依存の bug、API の仕様、互換）、コードに現れない不変条件や前提である
  - 書かない典型は、処理の逐語訳、識別子名の言い換え、セクション見出し、作業の実況（「〜を追加した」）である
  - 迷ったら書かない

## Git

- default branch へ直接 push せず、feature branch から PR を作る
- すべての commit に `git commit -s` で署名する
- commit message は英語で書く
- commit message には変更の Why と What だけを書き、How の箇条書きは付けない
- commit message に GitHub の予約語（Fixes、Closes、Resolves など）を書かない
  - 予約語は意図せず Issue を閉じる
- commit message に Issue や PR への参照（`#N`、`org/repo#N`、URL）を書かない
  - `#N` 参照は、commit が push されるたび Issue や PR のタイムラインに無駄な backlink を生む
  - Issue や PR への参照は PR body に置く（§PR description 参照）
- ready 後の修正は force-push で履歴を書き換えず、commit を足す
  - レビュアーが自分のレビュー以降の差分を追えるようにするためである

## Issue

- Issue は課題にフォーカスし、実装方法まで踏み込まない
  - 解決策を書き込みすぎると要件に見え、着手時の設計の幅を狭める
- 書くのは「何が問題か」「なぜ問題か」「どうなっていれば解決か」の 3 点である
  - 現状と問題は、観測した事実、再現手順、エラー出力で示す
  - なぜ問題かは、影響範囲と優先度の判断材料で示す
  - 期待する状態は How ではなく What で書く
- 調査で得た手がかり（該当コードの場所、原因の仮説）は着手者に有用なので書いてよい
  - 要件と混ぜず調査メモとして書き、観測した事実と仮説を分ける
- 解決アプローチの提案、実装手順の指定、変更ファイルのリスト、コードレベルの詳細設計は書かない
  - いずれも着手時に決めるもので、「案」として書いても着手者を anchoring して幅を狭める
- Issue や PR への参照は `org/repo#N` 形式で書く（§PR description と同じ）
- リポジトリに Issue テンプレートがあればテンプレートに従い、このルールは各欄の埋め方の指針として適用する

## Pull Request

- PR は初回作成時に必ず draft で作る
- レビュー準備ができたら `gh pr ready` で draft を解除する
- 破壊的変更（major バージョン更新、API 削除、依存の大規模入れ替えなど）は単独 PR で出し、機能変更と混ぜない
- PR の merge 待ちの間に、その PR に依存する後続作業を stack して進めてよい
  - base を上流 PR の branch にする
  - 上流がマージされたら base を main に戻し、merge で追随する（force-push しない）
  - 直列にするのはユーザーが指示したときだけにする

### PR description

- 読み手は human レビュアーである
- merge 判断に必要な情報だけを書き、記録媒体として使わない
- 分量は diff の行数ではなく、レビュアーの判断負荷に比例させる
  - 機械的な大量変更は短く書く
  - レビュアーが判断に迷う数行こそ厚く書く
- 厚く書く前に「この diff でレビュアーが迷う点」を 1 つ具体的に挙げる
  - 挙がらなければ各節 1〜3 文に収める
  - 調査が難しかったことは厚く書く理由にならない（原因が判明した後の変更が自明なら短く書く）
- 書くのは、動機（1〜2 文）、アプローチ（箇条書き 5 点まで、per-file ではなく）、non-goals と follow-up（該当が無ければ節ごと省く）である
- 「特に見てほしい箇所」は、レビュアーの目を一点に引きたい具体的な理由があるときだけ足す
- 検証の節は独立に作らない
  - CI が示さない確認のうち、レビュアーが実際に出す疑問に答えるものだけを、該当アプローチの bullet に畳む
  - 「追加でこれも回して緑だった」は書かない（回した本数は論拠にならず、CI Green 以上の情報にならない）
- コマンドや出力の貼り付けは、レビュアーが再現する必要があるときだけにする
- 関連 Issue や PR へのリンクと GitHub の予約語（Closes など）は、PR body ではむしろ推奨する
  - 参照は `org/repo#N` のように org/repo まで明示し、番号だけの `#N` による取り違えを防ぐ
- ファイル別の変更列挙（diff の言い直し）、作業過程の物語（「まず調査し…」）、テンプレートに無い装飾や N/A 埋めの boilerplate は書かない
- 情報は寿命で置き場所を振り分け、PR body には merge 後に価値が消える情報だけを書く
  - 症状、原因分析、再現手順は Issue に置き、PR からはリンクするだけにする
  - コードの特定箇所に紐づく非自明な Why はコードコメントに置き、PR body で繰り返さない
  - 変更自体の Why（なぜ今か、なぜこの方針か、捨てた代替案）は commit message に置く
  - レビュー時にだけ意味がある情報（CI で示せない検証の結論、注視点、リスク）は PR body に置く
- 原因分析や再現手順が Issue 側に無い、あるいは誤っている場合は、PR body で埋め合わせる前にユーザーに相談する
  - PR を作る流れで Issue に書き込みが入るのは、予想しにくい副作用になる
- リポジトリに PR テンプレートがあればテンプレートに従い、このルールは各欄の埋め方の指針として適用する

## 役割分担

- Why と What はユーザーと main セッションで決める
  - to-be を 1 文で言えるまで詰める
  - Issue や prompt に書かれていなければ、推測で埋めずにユーザーに聞く
- How は main セッションが持つ
  - 手順、分解、検証の設計は main の責務で、ユーザーに承認を求めない
  - 設計を左右する仮定だけは、着手前に該当コードを読むか 1 回動かして証拠にする
- 「〜を調べたい」「〜について考えたい」は調査依頼として扱い、成果物を作らず結論と根拠で終える
- 完了は自己申告ではなく実行結果で判定する
  - コードを変えたら動かして確かめ、コマンド、期待、実際を transcript に残す
  - 手順が要るときは `verify` skill を使う
- 同じバグへの修正が 2 回連続で失敗したら、3 回目に進む前に別モデルの視点（Claude Code では `codex` skill）を入れる

## レビュー

- commit 前の多段レビュー（観点別 fan-out、独立 reviewer、品質パスの skill）は行わない
  - 読んで見つかる誤りは、PR 上の Code Review agent と人間が担う
- commit 前に main が自分で diff を一度読み直す
- それ以上のレビュー層は、ユーザーが求めたときだけ足す
- `codex` は、別モデルと別 context の視点が要る設計判断やセカンドオピニオンに使い、定常工程にはしない
- ライブラリの API と使い方は Context7 MCP（`resolve-library-id` の後に `get-library-docs`）を優先する
- WebSearch は Context7 で解決できないときの最終手段にする
- 即時対応できる指摘はその場で直す
- 見送る指摘は、理由を添えてユーザーに判断を仰ぐ
- fail-open を勧める指摘はそのまま採らない
  - 採るなら「どの条件で通すか」を列挙し、その条件が既定経路にならないことを実際に発火させて確かめる

## サブエージェント

既定は single agent で、main が自分で読み、書き、動かす。
subagent を起こすのは次の 3 つが揃うときだけにする。

1. 互いに独立で並列に進められる作業がある（型、API の形、fixture のような短い契約を先に固定すれば独立になるものを含む）
2. subagent が main と異なる情報、model、tool、権限を持つ
3. agent を 1 つ足す利益が、token、待ち時間、誤り伝播のコストを上回る

同じ model と入力に役名だけを変えた「実装者と reviewer」は、2 を満たさないので理由にならない。

- agent を足す前に依存グラフを描く
  - 作業を書き込み先のファイル集合で分ける
  - ノード間の依存を「コードの依存」と「呼び出しや実行時の辺」に分ける
- 並列にするのは、コード依存が残らず、書き込み先も重ならないノードだけにする
  - 呼び出し辺だけが残るなら、被呼び出し側の型、シグネチャ、fixture を契約として先に凍結し、依存をその成果物へ移してから並列にする
- 次の編集が前の編集の実コードを必要とするなら、single のまま進める
- 2 つの作業が同じファイルに書くなら、single のまま進める
  - worktree は衝突を先送りするだけで消さない
- subagent に渡すのは契約（目的、対象ファイル、書き込み範囲、合格条件）と上流の成果物で、会話履歴は渡さない
- subagent に返させるのは patch、証拠、未解決事項で、transcript は返させない
- 統合と trunk への書き込みは main だけが行う
- 調査の fan-out は、1 件の lookup に 1 agent、比較に 2〜4、広い調査にだけ 10 以上を目安にする
- model と effort は agent 定義の既定に任せる
  - 起動時に変えたときは、理由を visible text に 1 行添える
- harness が agent 名を受け取る場合、名前は `<役割>` とし、model や effort を指定したときだけ `<役割>-<model>-<effort>` にする

## 開発手法

### AI と人間の役割分担

- AI が自走してよいのは、typo とコメントの修正、テスト名の変更、lint と format の機械的修正、既存パターンの拡張、テスト追加、依存バージョンの追従である
- 人間の判断を要するのは、新規依存の追加可否、テスト失敗の意味判定、既存の設計方針を変える変更である
- 上記以外でも、影響範囲が自明でない場合は自走せずユーザーに確認する

### 依存追加の判断

新しい依存（crate、npm パッケージ、CLI ツール、マネージドサービスなど）を追加する前に、次の順で確認する。

1. 標準ライブラリか既存依存で賄えないかを確認する
2. 追加するなら、メンテ状態、型定義、代替の有無を確認する
3. 判断に迷うときはユーザーに確認する

### 暗黙知と規約の置き場所

コードから読み取れない知識に気づいたとき、または規約を足したくなったときは、強制力が高く対象に近い置き場所を優先する。
下位で保持できるものを上位に上げない。
置き場所を強制力の高い順に並べると次になる。

1. コードで自明にする（アーキテクチャはディレクトリ構造、モジュール境界、型で、ドメイン用語は命名で表現し、守らせたい制約は誤りを選べない形にする）
2. lint やテストで機械的に落とす
3. 局所のコードコメント
4. `docs/`（コードに現れない業務知識、用語集）
5. path scoped rules や nested `AGENTS.md`
6. プロジェクト root の `AGENTS.md`
7. グローバル `AGENTS.md`

- 上位ほど毎セッション読み込まれ、対象から離れるので陳腐化に気づけない
- アーキテクチャを散文で書く前に、ディレクトリ構造と型がそれを語れていないかを確認する
- 変更自体の Why は commit message に置く（§PR description の寿命による振り分けに従う）
- ユーザーが詰まった箇所は、推測困難な暗黙知である可能性が高い
  - それでも優先するのは文書化ではなく、コード側での解消である
- 規約（`AGENTS.md`、path scoped rules、skill、agent 定義）とコードコメントに 1 行足すときは、「これを書かないとどう壊れるか」に答えられることを条件にする
  - 答えられない典型は、harness が既に供給している記述（tool の description が指示済み）と、指示が無ければ model がそもそもやらない類である
  - コード自体はこの基準の対象外で、自己説明的にするための命名、型、構造は「書かなくても壊れない」ものを含んでよい
- 編集では削除、反転、移動を先に検討し、追加は最後に置く
  - 「削除した規約の後始末として足したガード」は、元の規約を消せば発生しない失敗を防ぐだけの死んだ記述になる
- 規約を削除するときは、その記述が運んでいた義務を列挙し、引き受け先を決める
  - 引き受け先が無いものは削除しない
  - 失われた義務は不在なので diff に現れず、レビューでも検出されない

### TDD (テスト駆動開発)

開発タスクは原則 TDD で行う。

#### 意図

- テストは変更を安全にするために書き、検証だけを目的にしない
- テストは AI への仕様書として機能するので、テスト名から仕様が読み取れる粒度で書く
- リファクタ時は、まず既存の動作を E2E やインテグレーションテストで担保してから内部を変える
- ロジックを純粋関数に抽出し、テスト戦略を重い E2E から軽いユニットテストへ移行できる設計を目指す

#### テストが落ちたときの判断

テスト側を機械的に書き換えて通すと誤った仕様が固定化されるので、行わない。
次の 3 分岐で判断し、不明確ならユーザーに確認する。

1. **仕様変更**：実装を正とし、テストを更新する
   - 手がかりは、実装が直近変更されていて、その変更が意図的に振る舞いを変えていることである
2. **実装バグ**：テストを正とし、実装を直す
   - 手がかりは、テストの期待値が仕様と一致していて、実装だけが外れていることである
3. **テストが間違っていた**：テストを書き直す（最も見逃されやすい）
   - 手がかりは、テストが実装の内部構造をなぞっているだけで、外から見た振る舞いを検証していないことである

#### サイクル

1. 既存テストが通る状態を確認する
2. 新機能や修正に対応するテストを書く
3. テストが失敗すること（RED）を確認する
4. テストを通すための最小限のコードを書く
5. テストが通ること（Green）を確認する
6. コードを整理し改善する
7. リファクタ後もテストが通ることを確認する
