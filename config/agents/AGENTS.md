# AGENTS.md

## Common

- 会話は日本語で行う（Thinking は英語でもよい）
- 日本語を書くときは `japanese-tech-writing` skill を読み、その規範に従う
- 絵文字は使わない（Artifact の favicon のように機構が必須とするものは対象外）
- PR、Issue、docs の言語は repository の公開範囲で決め、public は英語、internal と private は日本語にする
- Codex では、変更対象の言語に対応する `~/.agents/rules/<language>.md` があれば作業前に読む
  - Claude Code は同じ本文を path-scoped rule として自動で受け取る
- 書ける分量の上限は、結論を支える証拠の量である
  - 断定は、読んだコード、実行した出力、ユーザーの明示発言で直接確認した範囲にだけ使い、それ以外は仮説か提案として書く
  - 渡された「確認済み」は、添えられた証拠が支える範囲でしか引き継がない
- コードの位置は既定では書かず、必要なときだけ commit を固定した GitHub の permalink にする（引用したツール出力の中の行番号は残す）
- コードコメントは英語で書き、コードから読み取れないこと（この形を選んだ理由、外部由来の制約、コードに現れない不変条件）だけに絞る
  - 命名、型、構造で説明できるものはコメントを足さずそちらを直し、迷ったら書かない

## Git と GitHub

- default branch へ直接 push せず、feature branch から PR を作る
- すべての commit に `git commit -s` で署名する
- commit message は英語で書き、変更の Why と What だけを載せる
- commit message に GitHub の予約語（Fixes、Closes、Resolves など）と Issue や PR への参照（`#N`、`org/repo#N`、URL）を書かない
  - 予約語は意図せず Issue を閉じ、`#N` 参照は push のたびに Issue や PR のタイムラインへ backlink を生む
- PR は draft で作る
- Issue の本文は `issue` skill、PR の作成と本文は `pull-request` skill に従う

## 役割分担

- Why と What はユーザーと main セッションで決め、to-be を 1 文で言えるまで詰める
  - Issue や prompt に書かれていなければ、推測で埋めずにユーザーに聞く
- How は main セッションが持ち、手順、分解、検証の設計にユーザーの承認を求めない
  - 設計を左右する仮定だけは、着手前に該当コードを読むか 1 回動かして証拠にする
- ユーザーの判断を要するのは、新規依存の追加、テスト失敗の意味判定、既存の設計方針を変える変更、影響範囲が自明でない変更である
  - 新しい依存は、標準ライブラリや既存依存で賄えないことを確認してから可否を聞く
- 「〜を調べたい」「〜について考えたい」は調査依頼として扱い、成果物を作らず結論と根拠で終える

## 検証とレビュー

- 完了は自己申告ではなく実行結果で判定し、コードを変えたら動かして確かめ、コマンド、期待、実際を transcript に残す
  - 手順が要るときは `verify` skill を使う
- commit 前のレビューは main が diff を一度読み直すだけにし、それ以上の層はユーザーが求めたときだけ足す
  - 読んで見つかる誤りは、PR 上の Code Review agent と人間が担う
- `codex` skill は、設計判断のセカンドオピニオンや、同じバグへの修正が 2 回連続で失敗したときなど、別モデルの視点が要るときだけ使う
- ライブラリの API と使い方は Context7 MCP を優先し、WebSearch は最終手段にする
- レビュー指摘は、即時対応できるものはその場で直し、見送るものは理由を添えてユーザーに判断を仰ぐ

## サブエージェント

既定は single agent で、main が自分で読み、書き、動かす。
subagent を起こすのは次の 3 つが揃うときだけにする。

1. 互いに独立で並列に進められる作業がある
2. subagent が main と異なる情報、model、tool、権限を持つ（同じ model と入力に役名だけを変えた「実装者と reviewer」は満たさない）
3. agent を 1 つ足す利益が、token、待ち時間、誤り伝播のコストを上回る

- agent を足す前に、作業を書き込み先のファイル集合で分け、ノード間の依存を「コードの依存」と「呼び出しや実行時の辺」に分けた依存グラフを描く
- 並列にするのは、コード依存が残らず、書き込み先も重ならないノードだけにする（worktree は衝突を先送りするだけで消さない）
  - 呼び出し辺だけが残るなら、被呼び出し側の型、シグネチャ、fixture を契約として先に凍結し、依存をその成果物へ移してから並列にする
- subagent に渡すのは契約（目的、対象ファイル、書き込み範囲、合格条件）と上流の成果物で、会話履歴は渡さない
- subagent に返させるのは patch、証拠、未解決事項で、transcript は返させない
- 統合と trunk への書き込みは main だけが行う
- 調査の fan-out は、1 件の lookup に 1 agent、比較に 2〜4、広い調査にだけ 10 以上を目安にする
- model と effort は agent 定義の既定に任せ、起動時に変えたときは理由を visible text に 1 行添える

## テスト

- 開発は原則 TDD で行い、テストが失敗すること（RED）を確認してから実装する
- テストは AI への仕様書として機能するので、テスト名から仕様が読み取れる粒度で書く
- リファクタ時は、まず既存の動作を E2E やインテグレーションテストで担保してから内部を変える
- ロジックを純粋関数に抽出し、テスト戦略を重い E2E から軽いユニットテストへ移行できる設計を目指す
- テストが落ちたら、テスト側を機械的に書き換えて通さず、次の 3 分岐で判断し、不明確ならユーザーに確認する
  1. **仕様変更**：実装が直近変更されていて意図的に振る舞いを変えたなら、実装を正としてテストを更新する
  2. **実装バグ**：テストの期待値が仕様と一致していて実装だけが外れているなら、テストを正として実装を直す
  3. **テストが間違っていた**：テストが実装の内部構造をなぞっているだけで外から見た振る舞いを検証していないなら、テストを書き直す（最も見逃されやすい）

## 規約の置き場所

コードから読み取れない知識に気づいたとき、または規約を足したくなったときは、強制力が高く対象に近い置き場所を優先する。
上位ほど毎セッション読み込まれ、対象から離れるので陳腐化に気づけない。

1. コードで自明にする（アーキテクチャはディレクトリ構造、モジュール境界、型で、ドメイン用語は命名で表現し、守らせたい制約は誤りを選べない形にする）
2. lint やテストで機械的に落とす
3. 局所のコードコメント
4. `docs/`（コードに現れない業務知識、用語集）
5. path scoped rules や nested `AGENTS.md`
6. プロジェクト root の `AGENTS.md`
7. グローバル `AGENTS.md`

- 規約（`AGENTS.md`、path scoped rules、skill、agent 定義）とコードコメントに 1 行足すときは、「これを書かないとどう壊れるか」に答えられることを条件にする
  - 答えられない典型は、harness が既に供給している記述と、指示が無くても model がそもそもやらない類である
  - 自己説明的にするための命名、型、構造はこの基準の対象外である
- 編集では削除、反転、移動を先に検討し、追加は最後に置く
- 規約を削除するときは、その記述が運んでいた義務を列挙して引き受け先を決め、引き受け先が無いものは削除しない
  - 失われた義務は不在なので diff に現れず、レビューでも検出されない
