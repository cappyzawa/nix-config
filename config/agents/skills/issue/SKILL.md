# Issue

Issue は課題を伝える文書で、解決策の設計書ではない。
解決策を書き込みすぎると要件に見え、着手時の設計の幅を狭める。
簡潔に書き、次に挙げる情報だけを載せる。

## 書くこと

- 課題を 1 節に収め、観測した事実、再現手順、エラー出力に続けて、誰がどう困っているかと優先度の判断材料まで書く
  - 現状と影響を別見出しに割ると、同じ材料を 2 度書くことになる
- 期待する状態を、How ではなく What で書く

## 書いてよいこと

- 調査で得た手がかり（該当コードの場所、原因の仮説）は着手者に有用なので書いてよい
- 手がかりは要件と混ぜず調査メモとして書き、観測した事実と仮説を分ける

## 書かないこと

- 解決アプローチの提案、実装手順の指定、変更ファイルのリスト、コードレベルの詳細設計は書かない
  - いずれも着手時に決めるもので、「案」として書いても着手者を anchoring して幅を狭める

## 形式

- Issue や PR への参照は `org/repo#N` 形式で書く
- リポジトリに Issue テンプレートがあればテンプレートに従い、この規範は各欄の埋め方の指針として適用する
