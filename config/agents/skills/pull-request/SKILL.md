# Pull Request

PR body の読み手は human レビュアーで、merge 判断に必要な情報だけを簡潔に書く。
記録媒体としては使わない。

## 作成と運用

- PR は初回作成時に必ず draft で作り、レビュー準備ができたら `gh pr ready` で解除する
- 破壊的変更（major バージョン更新、API 削除、依存の大規模入れ替えなど）は単独 PR で出し、機能変更と混ぜない
- ready 後の修正は force-push で履歴を書き換えず、commit を足す
- PR の merge 待ちの間に、その PR に依存する後続作業を stack して進めてよい
  - base を上流 PR の branch にする
  - 上流がマージされたら base を main に戻し、merge で追随する（force-push しない）
  - 直列にするのはユーザーが指示したときだけにする

## 本文に書くこと

- 動機を 1〜2 文で書く
- アプローチを箇条書き 5 点までで書き、per-file の列挙にはしない
- non-goals は該当があるときだけ節を作る
- follow-up の節に書くのは、検証の surface が違うかユーザーの判断が要るために別 PR にしたものだけで、それ以外は本 PR に含めるか捨てる
- 関連 Issue や PR へのリンクと GitHub の予約語（Closes など）は PR body ではむしろ推奨する
  - 参照は `org/repo#N` のように org/repo まで明示し、番号だけの `#N` による取り違えを防ぐ

## 分量

- 分量は diff の行数ではなく、レビュアーの判断負荷に比例させる
- 厚く書く前に「この diff でレビュアーが迷う点」を 1 つ具体的に挙げ、挙がらなければ各節 1〜3 文に収める
- 調査が難しかったことは厚く書く理由にならない
- 「特に見てほしい箇所」は、レビュアーの目を一点に引きたい具体的な理由があるときだけ足す
- 検証の節は独立に作らず、CI が示さない確認のうちレビュアーが実際に出す疑問に答えるものだけを該当アプローチの bullet に畳む
- 「追加でこれも回して緑だった」は書かない
- コマンドや出力の貼り付けは、レビュアーが再現する必要があるときだけにする

## 書かないこと

- ファイル別の変更列挙（diff の言い直し）
- 作業過程の物語（「まず調査し…」）
- テンプレートに無い装飾や N/A 埋めの boilerplate

## 情報の置き場所

PR body には merge 後に価値が消える情報だけを書き、寿命の長い情報は次の場所へ振り分ける。

- 症状、原因分析、再現手順は Issue に置き、PR からはリンクするだけにする
- コードの特定箇所に紐づく非自明な Why はコードコメントに置く
- 変更自体の Why（なぜ今か、なぜこの方針か、捨てた代替案）は commit message に置く
- レビュー時にだけ意味がある情報（CI で示せない検証の結論、注視点、リスク）は PR body に置く
- 原因分析や再現手順が Issue 側に無い、あるいは誤っている場合は、PR body で埋め合わせる前にユーザーに相談する
  - PR を作る流れで Issue に書き込みが入るのは、予想しにくい副作用になる

## 形式

- リポジトリに PR テンプレートがあればテンプレートに従い、この規範は各欄の埋め方の指針として適用する
